### 9076-r1-j01  `backend/internal/adapters/device/local/provider.go:1035`

If `recordBoots` fails after AO's own boot, the next look replaces the hub

`Boot` clears `ownBoots` in its defer whether or not `recordBoots` stored the new boot. `recordBoots` returns silently on a `simctl` error, a timeout or an empty result (`provider.go:1122-1125`). In that case `bootIDs` still holds the previous boot, so the next `NoteBooted` sees a change with no mark and restarts the hub, which drops all viewers. That happens right after AO's own successful boot, and the log says 'booted outside AO'. This is rare, but when it hits the effect is a silent, disruptive restart. A fix is to have `Boot` keep the mark, or fall back to `NoteBooted` with the `BootID` it can read, when recording fails.

Separately, the deferred cleanup at `provider.go:972` and the `recordBoots` call at `:1038` both read `device.ID` after `device.ID = res.ID` (`:1008`). Capturing the ID once next to `expectBoot` would keep the mark and the cleanup on the same key.

### 9076-r1-j02  `backend/internal/adapters/device/local/provider.go:253`

Asynchronous recordBoots at hub start can overwrite a newer boot id

The goroutine at lines 254-258 runs simctl and then writes `p.bootIDs` for every simulator unconditionally (lines 1131-1136). It runs concurrently with `Boot`. If its simctl read happens before a boot that `Boot` then records via `recordBoots(..., device.ID)` (line 1038), and its write lands after that, `bootIDs` ends up holding the older id. The next `NoteBooted` then sees a changed boot with `ownBoots` already cleared, and restarts the hub for a boot AO made itself. The window is small. Is it worth recording synchronously, or only writing ids for simulators not yet in the map?

### 9076-r1-j05  `backend/internal/adapters/device/local/provider.go:1106`

**Track a boot change that arrives during a hub replacement.**

`NoteBooted` stores a changed boot ID while `replacingHub` is true, but it does not schedule a replacement. When a simulator reboots after the new hub's helpers exist and before `restartHub` clears `replacingHub`, the stored ID matches the new boot. Later looks see no change, so no replacement runs. The rebooted simulator keeps touch input routed to the helper from the previous boot until another boot or a hub restart.

The required behavior has two parts:

- A boot change observed during a replacement must still trigger a replacement after the current one finishes.
- A look with no boot change must not schedule a replacement.

The design choice is open. One option is to record a pending change while `replacingHub` is true and check it when the replacement ends. The asynchronous `recordBoots` at lines 254-258 is not awaited, so the fix should not assume its timing.

### 9076-r1-j06  `backend/internal/adapters/device/local/provider.go:1171`

Hub replacement kills the hub under unrelated in-flight work

`restartHub` cancels the one shared hub and leaves `p.hub` nil until `EnsureReady` finishes, which can take up to 5s plus the 2-minute context. Everything else that uses the hub in that window fails. That includes another session's `Boot` of a different simulator. If `Boot` fails at the grid-start step (`provider.go:1019-1030`) and `startedHere` is true, it shuts that second simulator down and returns an error, so an unrelated user action fails because of someone else's outside boot. The window is bounded, so I rate it a judgement call. The restart could wait for in-flight `Boot` calls to finish, for example by tracking a count of boots in progress, or at least be logged and documented as disruptive.
