### 8764-r1-j01  `packages/mobile/lib/UpdateScreen.tsx:94`

Failed restart is silent and `applyUpdate` can be re-entered by a quick double tap

`applyUpdate` (`updateScreenState.ts:61`) sets the restarting phase and sleeps 900 ms before reloading, with no guard against a second call. The "Restart to update" button only becomes inert after the re-render sets `pointerEvents="none"`, so a fast double tap, or the Settings row plus the modal, can call `reloadIntoUpdate` twice, reload twice, and race the save and remove of the resume record. If the reload rejects, the screen disappears and the only trace is a `console.warn` (here and `settings/index.tsx:464`), so the user is not told the restart did not happen. A re-entry guard (return early when the phase is already `restarting`) and a visible error would cover both.

### 8764-r1-j08  `packages/mobile/lib/UpdateRouteKeeper.tsx:43`

Resume route is consumed at launch but applied after an unbounded wait, and can replace the page the user navigated to

`takeResumeRoute()` deletes the record and checks the 2-minute age at launch (updateResumeStore.ts:38-43), but the navigation happens only once `config !== null` (line 44). `config` stays null whenever the selected machine does not answer: `resolveActiveConfig` returns null for an unreachable or failed host (resolveConfig.ts:55-60), and the store sets `config` to null on every backgrounding (store.tsx:654). So with the machine offline or slow, the age limit is never checked again. When the machine answers later, even minutes later, `restoreAction` runs against whatever page the user is on by then. If they have opened another page, it returns "replace" and that page is swapped for the saved one. The user gets an unexpected jump or loses their place, with no error. This contradicts the doc on `RESUME_MAX_AGE_MS`, which says a saved page must not reopen later as a surprise. Fix: keep the record's `at` and drop the restore once it is older than `RESUME_MAX_AGE_MS` when the effect finally runs. Also only "replace" when the user has not navigated since launch. The `replace` branch exists for the stale deep link that expo-router reopens after a reload (updateResume.ts:63-67), so keep it for that case.

### 8764-r1-j09  `packages/mobile/lib/UpdateRouteKeeper.tsx:43`

Resume waits on `config !== null`, which never happens for an unpaired or cloud-only user, then fires whenever it does

The saved page is consumed from storage at launch (`takeResumeRoute` removes the record and `decodeResumeRoute` checks its age once, `UpdateRouteKeeper.tsx:32`). The restore then waits for `config === null` to end (line 43). In `store.tsx`, `config` is `useState<ServerConfig | null>(null)` (line 392) and stays null with no paired machine selected. The store exposes a separate `configResolved` flag for exactly this case (`store.tsx:393-395`, "distinguishes 'no config yet' from 'no machine paired'"). Two consequences: (1) a user with no paired machine, or one whose host is unreachable, who restarts from a page like Settings never gets that page back; (2) the in-memory `saved` value has no age check, so if that user later pairs a machine in the same session, `config` turns non-null and the stale page is pushed over whatever they are doing. Gate on `configResolved` instead of `config === null`, so the restore runs once resolution has finished with or without a machine. If a page truly needs the machine, it should handle a missing one itself. Alternatively re-check the age when it fires.
