### 8720-r1-i01  `backend/internal/session_manager/manager.go:2275`

**Resolve the start commit once in `createWorkspaceProjectRepo`.**

`createWorkspaceProjectRepo` resolves `baseRef` to `baseSHA` at line 1873. It then passes the symbolic `seedRef` to `addWorktree` at line 1879. Git resolves `seedRef` when `git worktree add` runs, which is after the capture. If another update moves `origin/` between these steps, the worktree starts at the new commit while `BaseSHA` records the old one. Git ref locks do not prevent this, because they protect each ref update, not the sequence.

The new background fetch adds a writer that can run in this window. The window is narrow, so the effect is a wrong recorded base and a possibly inaccurate session diff, not a broken worktree.

Resolve the start ref to a SHA once. Pass that SHA to `addWorktree`. When the start ref and the base ref name the same ref, reuse that SHA as `BaseSHA`. Keep the symbolic refs for `BaseRef` and branch identity. The single-repository path (lines 368–380) and the `creationSHA` capture before `createWorkspaceProjectRepo` (line 594) use the same pattern and need the same change.

### 8720-r1-i02  `backend/internal/adapters/workspace/gitworktree/workspace.go:2062`

Repos with no usable cached HEAD pay a full lookup on every start, and the 5s bound is per repo

`resolveAutomaticDefault` only short-circuits when `Inspect` succeeds (workspace.go:2055). A repo with no cached HEAD (a never-fetched clone, or an offline first run) falls through to `Resolve` on every start, even inside `automaticDefaultRecheck`. The comment at 2063-2064 says an offline machine does not start another lookup for every start in the window. That holds only when a cached HEAD exists.

The 5s budget is created per `ResolveDefaultBranch` call (workspace.go:198). The caller loops over all targets before its shared `fetchCtx` starts (manager.go:2236-2251). The worst case for a workspace project with N unreachable, uncached child repos is therefore about N×5s of resolution, then up to 5s of fetches, on every spawn.

That is still better than the old unbounded `Resolve(ctx, ctx, ...)`. The comments at manager.go:2234-2235 ("which the adapter bounds") and workspace.go:2063 overstate the bound. Either tighten the comments, or share one deadline across the targets in the resolve loop. A negative cache for failed lookups is another option.

### 8720-r1-i03  `backend/internal/adapters/workspace/gitworktree/workspace.go:198`

**Bound the default-branch resolution loop with one shared deadline.**

`ResolveDefaultBranch` gives each call its own 5s budget. The manager calls it once per target in a sequential loop, and it creates the shared fetch deadline only after that loop. A repository without a usable cached HEAD waits up to 5s for its live lookup. If three such child repositories have unresponsive remotes, resolution alone can take about 15s before the fetch deadline starts. Repositories with a usable cached HEAD return at once and are not affected.

Apply one aggregate budget to resolution and fetching together. Each lookup must stop at that shared deadline. When the budget expires, resolution must keep the local refs instead of waiting further. The workspace project preparation path already resolves child bases under one shared `remoteCtx` for the same purpose.


### 8720-r1-i04  `backend/internal/session_manager/manager.go:2274`

Overlapping background fetches of the same base are possible

`defaultBranchFetchedRecently` stamps `defaultBranchFetchedAt` when the fetch is attempted. The background fetch is allowed up to `defaultBranchBackgroundFetchTimeout` (1 min, manager.go:2324), but the skip window is only 30s. A slow fetch that is still running at +30s lets the next start launch a second `git fetch` of the same refspec (`defaultBranchFresh` is still true because freshness is only recorded on success). Two concurrent fetches into the same remote-tracking ref can hit ref-lock contention. The loser is only logged as a warning, so it self-heals. An in-flight marker per key, or recording the attempt time as the dedupe key until the fetch completes, would avoid it.

### 8720-r1-i07  `backend/internal/gitdefault/resolver.go:219`

**Fetch a changed default branch before caching it as remote HEAD.**

`RefreshRemoteHead` skips the fetch whenever `refs/remotes//` already exists. If the remote renames its default branch from `main` to `develop` and an old `origin/develop` ref remains, the method caches `develop` as HEAD without fetching it. Worktree creation then resolves that cached HEAD and can start from the stale `origin/develop` commit, even though the spawn just fetched `main`. The next start fetches `develop` and corrects the base, so the stale base affects only that start.

Fetch the advertised branch when the cached HEAD names a different branch. Keep the skip when the cached HEAD already names it.

### 8720-r2-i01  `backend/internal/session_manager/manager.go:2235`

One stalled repo makes later repos fail resolution instead of getting their own lookup

Resolution now shares `fetchCtx` with the fetches. `resolveAutomaticDefault` (workspace.go:2058) answers from Git's cached HEAD when one exists, so only repos with no cached `origin/HEAD` reach `resolver.Resolve`. For those, the live lookup runs on `remoteCtx` (gitdefault/resolver.go:151). If an earlier repo's lookup uses the whole 5s, every later uncached repo starts with an expired `remoteCtx`. `Resolve` then falls to `cachedRemoteHead` and `initializedBeforeFirstPush` (resolver.go:178-187), and with neither it returns an unresolved error. The manager logs a warning and leaves `targets[i].resolved` empty. That repo gets no `baseRefs` entry and no fetch (line 2267). Before this change each repo got its own 5s lookup. This is the intended trade for bounding total latency, but it makes a worker's base-ref choice for children depend on the order of the repo list. Say so in the PR body, or decide whether a small per-repo floor is wanted.
