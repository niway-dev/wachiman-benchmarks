### 8764-r1-i02  `packages/mobile/lib/updateScreenState.ts:61`

applyUpdate is not re-entrant: a double tap on Restart reloads twice

`applyUpdate` always sets `restarting`, sleeps, and calls `reloadAsync`, even when a restart is already under way. The Restart button (UpdateScreen.tsx:92-97) only becomes non-pressable (`pointerEvents="none"`, line 89) after React re-renders from the store change. A second tap in that window starts a second `applyUpdate`. That runs `reloadIntoUpdate` twice, writing the resume record and calling `Updates.reloadAsync` twice. If the reload fails, the first rejection hides the screen while the second call is still pending. `showUpdateReady` and `dismissUpdateScreen` already ignore calls while restarting. Make `applyUpdate` return early the same way, or share the in-flight promise.

### 8764-r1-i03  `packages/mobile/lib/UpdateScreen.tsx:90`

**Hide the restarting buttons from VoiceOver.**

When restarting begins, both buttons remain mounted and enabled. `importantForAccessibility="no-hide-descendants"` excludes them on Android only. In React Native 0.86.3, opacity changes the native layer separately from accessibility visibility. The hidden actions therefore lack the corresponding iOS exclusion. ([github.com](https://github.com/react/react-native-website/blob/main/website/versioned_docs/version-0.86/accessibility.md))

Add `accessibilityElementsHidden={restarting}` to this container. Keep the existing Android property. This removes the actions from VoiceOver during restart and restores them in the ready phase. ([reactnative.dev](https://reactnative.dev/docs/accessibility?utm_source=openai))

### 8764-r1-i04  `packages/mobile/lib/UpdateRouteKeeper.tsx:43`

Resume route is consumed at launch but applied after an unbounded wait, and can replace the page the user navigated to

`takeResumeRoute()` deletes the record and checks the 2-minute age at launch (updateResumeStore.ts:38-43), but the navigation happens only once `config !== null` (line 44). `config` stays null whenever the selected machine does not answer: `resolveActiveConfig` returns null for an unreachable or failed host (resolveConfig.ts:55-60), and the store sets `config` to null on every backgrounding (store.tsx:654). So with the machine offline or slow, the age limit is never checked again. When the machine answers later, even minutes later, `restoreAction` runs against whatever page the user is on by then. If they have opened another page, it returns "replace" and that page is swapped for the saved one. The user gets an unexpected jump or loses their place, with no error. This contradicts the doc on `RESUME_MAX_AGE_MS`, which says a saved page must not reopen later as a surprise. Fix: keep the record's `at` and drop the restore once it is older than `RESUME_MAX_AGE_MS` when the effect finally runs. Also only "replace" when the user has not navigated since launch. The `replace` branch exists for the stale deep link that expo-router reopens after a reload (updateResume.ts:63-67), so keep it for that case.

### 8764-r1-i05  `packages/mobile/lib/UpdateRouteKeeper.tsx:43`

**Gate the restore on the store's resolved load state, not on `config !== null`.**

`config` stays `null` after the store finishes loading when no machine is paired, when the app is in cloud-only scope, and after an endpoint is rejected. The guard at line 43 returns on each render in those cases, so `restored` never becomes `true` and the saved page is never reopened. Users in those states restart onto the default page instead of the page they were on. The stated behavior of the restart is not met for them.

The guard should wait only until the store has finished its first load. It should then proceed whether or not a machine is configured. The store already tracks this state in `configResolved`. Confirm that `useApp()` exposes this field before using it as the gate.
