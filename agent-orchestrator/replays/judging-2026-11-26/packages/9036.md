### 9036-r1-i03  `backend/internal/daemon/startup_timing.go:67`

**Preserve the step-total equality when converting to milliseconds.**

If two phases each take 1.5 ms, this line records 1 ms for each phase, but `payload` reports a 3 ms total. Independent integer conversions lose the fractional remainder. Go documents `Milliseconds` as an integer millisecond count. ([pkg.go.dev](https://pkg.go.dev/time?utm_source=openai))

Calculate each step as the difference between consecutive elapsed-millisecond endpoints. Add a fractional-millisecond regression case. This preserves the elapsed total and the existing whole-millisecond cases.

### 9036-r1-i06  `frontend/src/renderer/lib/launch-telemetry.ts:135`

**Keep close reporting active while launch steps are pending.**

For a cold launch, this new await runs after the `pagehide` listener has been removed. If the window closes while `launchSteps()` is pending, `sendOnClose` does not run. If the renderer is destroyed, the pending result cannot reach the caller either. Previously, no asynchronous collection remained after listener cleanup.

Keep the listener active until step collection completes. Then check `sentOnClose` before returning, so the normal and close paths cannot both report the launch.

### 9036-r1-i07  `frontend/src/renderer/lib/performance-telemetry.ts:312`

**Subtract post-layout script time from rendering, not from frame callbacks.**

`ResizeObserver` callbacks can run after `styleAndLayoutStart`. Line 312 classifies any script that starts at or after `tasksEnd` as callback time. Line 318 subtracts that total from the callback phase, which ends at `styleStart`. Line 319 counts the full `end - styleStart` as rendering. A script that starts after `styleStart` is therefore subtracted from the wrong phase, and its time remains in rendering.

For `startTime=100`, `duration=100`, `renderStart=110`, `styleAndLayoutStart=120`, and one 60 ms `user-callback` starting at 130 with no forced layout, the code reports:

- `unlisted` = 10 (line 317)
- `user-callback` = 60 (line 310)
- `frame-callbacks` = 0, because 120 − 110 − 60 = −50 is ignored by `add`
- `rendering` = 80 (line 319)

That totals 150 ms for a 100 ms frame. The 60 ms script is counted in both the script cause and rendering. The 10 ms interval from 110 to 120 is lost.

Subtract each script only from the phase it occupies. Scripts that start at or after `tasksEnd` and before `styleAndLayoutStart` should reduce `frame-callbacks`. Scripts that start at or after `styleAndLayoutStart` should reduce `rendering`. Keep the pre-layout callback interval as `frame-callbacks` after subtracting only the scripts in that interval. For the example, this gives 10 unlisted, 60 user-callback, 10 frame-callbacks, and 20 rendering, which totals 100 ms.

### 9036-r1-i08  `frontend/src/renderer/lib/launch-telemetry.ts:135`

The steps IPC runs after the usable-wait race and the pagehide handler are gone, with no bound of its own

`launchProperties` bounds the wait with the race at lines 117-130, then removes the `pagehide` listener (line 132) and awaits `readLaunchSteps()` (line 135). That IPC call is outside both the 60 s bound and the close-time handoff. If the window closes during this await (normally a few ms, longer if main is busy at startup), the event is lost: `sendOnClose` is no longer registered and a page-lifetime promise is dropped. Before this change the properties were computed synchronously after the race, so this gap did not exist. Fix: read the steps before the race, or in parallel with it (cold launch only), so the `pagehide` handler can include them, or race the IPC with a short timeout.
