### 9076-r1-i01  `backend/internal/adapters/device/local/provider.go:1038`

**Record the boot that received the fresh helper.**

If an outside reboot occurs after `grid/api/start` succeeds but before this call, `recordBoots` accepts the outside boot as the helper's boot. During this interval, `ownBoots` also suppresses replacement. Later observations match the recorded ID, so touch recovery never starts.

Capture the boot associated with helper creation. If the boot changes afterward, keep that change pending for recovery. Do not accept a later boot merely because `Boot` has reached its final recording step. The asynchronous hub-start recording needs the same ownership rule.

### 9076-r1-i02  `backend/internal/adapters/device/local/provider.go:1106`

**Track a boot change that arrives during a hub replacement.**

`NoteBooted` stores a changed boot ID while `replacingHub` is true, but it does not schedule a replacement. When a simulator reboots after the new hub's helpers exist and before `restartHub` clears `replacingHub`, the stored ID matches the new boot. Later looks see no change, so no replacement runs. The rebooted simulator keeps touch input routed to the helper from the previous boot until another boot or a hub restart.

The required behavior has two parts:

- A boot change observed during a replacement must still trigger a replacement after the current one finishes.
- A look with no boot change must not schedule a replacement.

The design choice is open. One option is to record a pending change while `replacingHub` is true and check it when the replacement ends. The asynchronous `recordBoots` at lines 254-258 is not awaited, so the fix should not assume its timing.

### 9076-r1-i03  `backend/internal/adapters/device/local/provider.go:1103`

**Reject stale observations before changing the recorded boot.**

A `LiveLease` request can retain boot A while another request observes boot B and completes hub recovery. If the first request resumes afterward, this assignment replaces B with A and starts another hub replacement. That replacement interrupts every device stream even though the hub is already healthy.

Carry an observation generation through listing and notification, or revalidate the observation before using it to replace the hub. Preserve recovery for a genuinely newer outside boot.


### 9076-r1-i04  `backend/internal/adapters/device/local/provider.go:1161`

Hub replacement does not wait for in-flight hub work, and takes down every device's stream

`restartHub` cancels the hub (line 1161) and sets `p.hub = nil` (1167-1169) with no regard for other calls using it. `Hub()` then answers "device support is not running" (line 581) until `EnsureReady` finishes, which can take up to the 2 minute context at 1171. A `Boot` for a different simulator or session that is mid-flight (`/api/devices/boot`, grid start, `resetSimulatorHelper`, lines 986-1015) then fails. On that failure `Boot` tries `p.Shutdown` through the same dead hub (1024), so a simulator it powered on can be left running with no lease. The user sees an error, not silent corruption. One outside boot of simulator X also drops the streams of every other simulator and emulator. Consider skipping the replacement while any `Boot` is running (`ownBoots` is non-empty), or retrying the replacement afterwards. Also say in the NoteBooted doc that every viewer reconnects, not just the rebooted device's.

### 9076-r1-i05  `backend/internal/adapters/device/local/provider.go:253`

Asynchronous recordBoots at hub start can overwrite a newer boot id

The goroutine at lines 254-258 runs simctl and then writes `p.bootIDs` for every simulator unconditionally (lines 1131-1136). It runs concurrently with `Boot`. If its simctl read happens before a boot that `Boot` then records via `recordBoots(..., device.ID)` (line 1038), and its write lands after that, `bootIDs` ends up holding the older id. The next `NoteBooted` then sees a changed boot with `ownBoots` already cleared, and restarts the hub for a boot AO made itself. The window is small. Is it worth recording synchronously, or only writing ids for simulators not yet in the map?
