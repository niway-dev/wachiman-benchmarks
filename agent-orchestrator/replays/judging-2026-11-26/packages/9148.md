### 9148-r1-i05  `packages/mobile/lib/spawn-composer.tsx:242`

The panel element is memoized on `[items, select, show]`, and `select` (line 228-239) depends on `onChangePrompt`. The page passes `onChangePrompt={edited(setPrompt)}` (app/spawn.tsx:1094), and `edited` (spawn.tsx:728) returns a new function on every `SpawnPage` render. The controls files forward it unchanged (spawn-composer-controls.ios.tsx:176), so there is no memo to stop it.

While the list is shown, the loop runs like this:
1. `SpawnPage` renders and hands the composer a new `onChangePrompt`.
2. `select` changes, so `skills.panel` is a new element.
3. The effect at line 100 calls `overlayHost({ panel, composerHeight })` with a new object.
4. That is `setSuggestionOverlay` in the page (spawn.tsx:705), which re-renders `SpawnPage` and returns to step 1.

The comment at line 240-241 says a new element each render "would loop". It does loop here, because the memo is defeated by the unstable callback. The composer tests don't catch it: they use a stable `onChangePrompt` and a stable `host`.

Fix: keep the latest `onChangePrompt` in the `latest` ref and make `select` stable (`useCallback(..., [])`). Alternatively wrap `edited(setPrompt)` in `useCallback` in spawn.tsx. Prefer the first, since the hook then no longer depends on how the caller builds its handlers.

### 9148-r2-i01  `packages/mobile/lib/chat/useConversation.ts:237`

**Keep skills associated with their reporting harness before returning them.**

When a loaded `claude-code` chat changes to `codex`, the first render contains the new harness and the old `skills`. `setSkills([])` schedules another render; it does not change the values captured by that render's effects. ([react.dev](https://react.dev/reference/react/useEffect?utm_source=openai))

The supplied `ChatSessionScreen` effect therefore remembers the old list under `codex`. The next empty list cannot remove it because `rememberChatSkills` ignores empty lists.

Store the reporting harness with the skills. Return an empty list whenever that harness differs from the current snapshot harness. This preserves unchanged-agent suggestions and prevents the incorrect remembered write before the new agent loads.

### 9148-r2-i02  `packages/mobile/lib/chat/useConversation.ts:237`

Clearing skills at an agent switch still lets the old list be remembered under the new agent

The switch effect (useConversation.ts:216-238) calls `setSkills([])`, but the state only changes on the next render. `ChatSessionScreen.tsx:379-382` runs `rememberChatSkills(host, skillsHarness, projectId, conversation.skills)` in an effect with `skillsHarness` and `conversation.skills` as dependencies. `skillsHarness` comes from `conversation.snapshot?.harness`, which changes in the same commit as the switch. In that commit the screen's effect fires with the new harness (e.g. codex) and the outgoing agent's `conversation.skills` (claude-code), because the hook's `setSkills([])` has not applied yet. That stores claude's list under the codex key. The follow-up render passes `[]`, which `rememberChatSkills` ignores (`!skills.length`). The New task page (`rememberedChatSkills`, used in `spawnSkills.ts:20`) then offers claude's skills for codex until a codex chat reports its own list. That is the cross-agent leak this PR sets out to close. The new test only checks `conversation.skills` and never the remembered list, so it does not catch this. A fix is to remember only skills that were loaded for the harness shown, for example by having the hook expose the harness its `skills` belong to and having the screen pass that to `rememberChatSkills`. I did not run this, so the ordering rests on React's effect and state semantics.

Also: `rememberedSkills.test.ts` does not cover this path.
