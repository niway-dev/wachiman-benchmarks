### 9095-r1-i03  `backend/internal/service/chat/skill_scan.go:51`

ScanSkills does filesystem I/O with no context and no time bound

AGENTS.md says functions that do I/O take `context.Context` first. `ScanSkills` does about two `ReadDir`s per root, a `Stat` per entry, and up to 64 KiB read per skill file. It also reads three settings files and the plugin manifests. All of that runs inline in the HTTP handler with no deadline. The sibling `Service.Skills` bounds its provider read with `skillsListTimeout` (`skills.go:24`). Here the only limit is the number of entries. A large plugin cache, or a home directory on a slow or stalled network mount, holds the request for as long as the filesystem blocks. When the client aborts (the query passes `signal`), the handler keeps scanning. The new chat page then shows the previously reported list (or none) with no indication. Pass `r.Context()` through and check it between roots.

### 9095-r2-i01  `backend/internal/service/chat/skill_scan.go:299`

Symlinked commands folder now yields no commands

The old code listed a commands root with `os.ReadDir(root.dir)`, which follows a symlink at the root. The new `commandFiles` uses `filepath.WalkDir`, which calls `os.Lstat` on the root and does not follow a symlink there. If `~/.claude/commands` or `<workspace>/.claude/commands` is a symlink to a directory (common with dotfile managers), the callback sees one non-directory entry named `commands`. That entry does not end in `.md`, so the function returns nothing. The user's commands silently vanish from the pre-session `/` menu. The skills branch still uses `os.ReadDir` plus `os.Stat`, so only commands regress. Resolve the root first, for example with `filepath.EvalSymlinks(dir)`, before walking, or walk the path with a trailing separator. Add a test with a symlinked commands root.

### 9095-r2-i02  `backend/internal/service/chat/skill_scan.go:299`

**Resolve a symlinked commands root before walking it.**

`filepath.WalkDir` does not follow symbolic links, and the root entry is checked as a symlink rather than a directory. When `~/.claude/commands` is a symlink to a directory, the walk does not enter the target. The callback can then discover no commands, even when the target contains valid Markdown command files. Claude Code can load commands from this layout, so this scanner can omit them.

Resolve `dir` with `filepath.EvalSymlinks` before calling `filepath.WalkDir`, and walk the resolved path. Compute command names relative to the resolved root so existing names, such as `ns:cmd`, do not change.

### 9095-r2-i03  `backend/internal/service/chat/skill_scan_test.go:179`

**Build the installed-plugins fixtures with `json.Marshal`, not string concatenation.**

Windows temporary directory paths contain backslashes. Inserting them directly into a JSON string literal creates invalid escapes such as `\U`. The malformed `installed_plugins.json` then fails to decode. `ScanSkills` treats that failed read as a reason to return without discovering the plugins, so the assertion at line 183 fails on Windows.

The same pattern appears at lines 46-47, 79, and 117-118. Build each of these fixtures with `json.Marshal`, or otherwise escape the path values, so the paths are preserved on both Windows and Unix.

This fails only in local Windows runs of this package. The checked CI workflows do not run `internal/service/chat` on Windows.
