### 🟠🐛 **Fix · bug: A failed card load leaves the floating card dead for the session, with no in-app fallback (confidence medium)**

`apps/kaipu-record/src/main/recording/recording-ready-window.ts:265`

`load` fires the card page with `void browserWindow.loadFile(...)` (line 265; the `loadURL` branch at 261 is the same), so a rejected load is swallowed. `show()` returns `true` as soon as the window exists (line 146), before anything has painted. `present()` only paints once the card's renderer sends `recording-ready:card-ready`, which sets `rendererReady` (line 110, gate at 221). If the card page never loads, or its renderer crashes, `this.window` stays set and undestroyed, so every later `show()` also returns `true` and paints nothing. The page's hook therefore never falls back: `use-floating-ready-card.ts:26-28` only falls back on `false` or a rejected IPC, and its comment at lines 13-14 says the card is "never lost". The result is that the "Your video is ready" prompt is silently gone for the rest of the session. Fix: handle the load rejection and renderer loss in the window class (drop `this.window` so the next show recreates it), and have the `show` handler answer `false` when the first load fails, for example by awaiting the load before it resolves.

### 🟠🐛 **Fix · bug: Going Back to a recording's page floats the card again after the user already acted on it (confidence high)**

`apps/kaipu-record/src/renderer/src/pages/library-detail/library-detail-page.tsx:141`

`showCard` is true whenever the history entry's state carries `fromRecording` (library-detail-page.tsx:101, 130-134), and that state survives Back. `useFloatingReadyCard` keys its "asked" guard on `location.key` in a ref (use-floating-ready-card.ts:18-24). When the user goes Back to that entry, the request key changes back to the earlier entry's key (or the page remounts and the ref is gone), so `showRecordingReady` is called again and the card floats on the desktop again.

Repro: a take ends and the card floats; the user clicks Open (a hand-off navigates to `/library/:id` with no state, a new entry); they press Back; the earlier entry still has `fromRecording: true`; the card floats again. Same after a chip into Prepare followed by Back.

Fix: once the ask succeeds, drop the one-shot flag from the entry (for example `navigate(location.pathname, { replace: true, state: {} })`), or record the asked keys where they survive a remount. Keep the in-app fallback reachable when the ask fails. No test covers Back; add one next to the "falls back" test in library-detail-page.test.tsx.

### 🟠🐛 **Fix · bug: A floating window that never paints leaves no card for the rest of the session (confidence medium)**

`apps/kaipu-record/src/renderer/src/pages/library-detail/library-detail-page.tsx:155`

The page drops its in-app card as soon as `showRecordingReady` resolves true (library-detail-page.tsx:155). But main answers true as soon as the window object exists (recording-ready-window.ts:134-147), and it paints only after the card renderer reports ready (recording-ready-window.ts:219-226). `ensureWindow` reuses a live window (recording-ready-window.ts:175-176), and `rendererReady` only resets when the window closes or is recreated. So if the card page never loads (its `loadFile`/`loadURL` fails, the promise is `void`ed at recording-ready-window.ts:258-268), every later take answers true, nothing is shown, and the in-app fallback never runs for the rest of the session.

The doc's "Not done" entry (floating-ready-window.md:55-56) says the card shows nothing once, but the real scope is every later take until the app restarts. Fix: `show()` should answer true only after the card reports ready (with a bounded wait), or main should answer false when the load fails so the page falls back. Confidence is medium because I did not run the window; the state is read from the code above.

### 🟡🐛 **Consider · bug: Dropping a file on the floating card navigates that window away from the card (confidence medium)**

`apps/kaipu-record/src/renderer/src/main.tsx:66`

I found no `will-navigate` or drop guard in apps/kaipu-record/src/main or the renderer; the only `setWindowOpenHandler` is for the main window (main/index.ts:404), and the library's drop handler lives in the main window's renderer (use-file-drop.ts:31-51). If a video file is dropped on the card, Electron's default navigates that window to the file. The card disappears, and because `rendererReady` stays true (recording-ready-window.ts:219-226), later payloads go to a page with no listener while the window is shown with the video. The capture toast window has the same exposure, so the fix belongs in a shared place: prevent `dragover` and `drop` on the card window's document, or cancel `will-navigate` for it, in main.tsx's branch or where the window is created. Confidence is medium: this depends on Electron's default for file drops, which I did not run.
