### 🟠🐛 **Fix · bug: Shade window is reused for the whole session, but a renderer crash or failed load is never recovered (confidence high)**

`apps/kaipu-record/src/main/recording/recording-shade-window.ts:135`

`ensureWindow` returns the existing shade whenever it is not destroyed (line 135). Before this change `hide()` destroyed the window, so every take built a fresh one and a broken page was replaced on the next take. Nothing now replaces a bad page. The only listeners are `ready-to-show` and `closed` (lines 181-193): there is no `render-process-gone` or `did-fail-load` handler, and `loadFile` is `void`-ed (line 179). Electron keeps a window open when its renderer dies, so `closed` does not fire. Two silent outcomes follow:
- Initial load fails: `ready` stays false, so `show` never reaches `present`, `onShown` never runs, and the countdown waits for its timeout (`countdownVisible` in apps/kaipu-record/src/renderer/src/features/recording/recorder-store.ts:285-289). Nothing paints for the rest of the session.
- Renderer crashes after painting: `ready` stays true, `send` goes to a dead page, and `showInactive` shows the last painted frame.
The take still records, but the countdown dim, number and REC border are missing until restart. The capture overlay handles the same case for its persistent spares (apps/kaipu-record/src/main/screenshots/capture-overlay-windows.ts:657-670 drops the spare on `render-process-gone` and `did-fail-load`). Suggested fix: subscribe to `render-process-gone` and main-frame `did-fail-load` on the shade's `webContents` and destroy the window, so the existing `closed` handler clears `window`, `ready` and `visible` and the next `show` loads a new one.

### 🟡🧪 **Consider · tests: Test named for a crash only simulates `destroy()` (confidence high)**

`apps/kaipu-record/src/main/recording/recording-shade-window.test.ts:191`

A renderer crash keeps the window alive and emits `render-process-gone`, which is the case the window-reuse change breaks (see the finding on recording-shade-window.ts:135). The overlay test's fake already has `crashRenderer()` (apps/kaipu-record/src/main/screenshots/capture-overlay-windows.test.ts:59-62), which could pin the crash and failed-load cases once they are handled.

### 🟠🐛 **Fix · bug: Mic opened by the countdown's settings sync is not awaited before the take begins (confidence medium)**

`apps/kaipu-record/src/renderer/src/features/recording/recorder-store.ts:532`

`beginTake` calls `start.live?.sync(input)` (line 532) and then `prepared.begin()` (line 535) without waiting for anything `sync` started. `sync` -> `applyToggles` queues `handle.setMicrophoneEnabled(true, deviceId)` (lines 776-786) when the mic was off at acquisition, and the engine opens that device asynchronously (`recorder-engine.ts:558-575`, the `micMuteGain === null` branch). The forwarder only attaches at line 490, once acquisition resolves. So a mic switched on during the first second of the countdown, before the forwarder existed, starts the take with the mic not connected, and the first words are silently missing. The comment at lines 530-531 says the settings are brought in line 'before encoding', which the code does not guarantee for the mic. Fix: make `sync` return the queue promise and `await` it inside `began`, under the existing START_TIMEOUT race, so the take begins only once the device is open or the start fails visibly.

### 🟠❓ **Fix · question: A spare overlay stays blank if its first state is delivered before the subscription exists (confidence low)**

`apps/kaipu-record/src/renderer/src/features/screenshots/overlay/capture-overlay.tsx:277`

A `spare=1` window paints nothing until its first state arrives (`if (!received) return null`). Main sends that state from `reveal` on `ready-to-show` (`capture-overlay-windows.ts:684-691`). The renderer subscribes to `onState` in an effect (line 145-149) after an async bootstrap (`main.tsx:43-45`). If the state is sent before that effect runs, `received` never becomes true: the window is shown, transparent and blank, and it still takes clicks until Esc. Before this change a lost state left the overlay painted from its URL query. I did not read `I18nRoot` (`apps/kaipu-record/src/renderer/src/app/i18n-root.tsx`), which decides when the React tree first commits. Is there a guarantee that `onState` is subscribed before `ready-to-show`?

### 🟠❓ **Fix · question: The recording shade now depends on a state IPC that may land before its listener (confidence low)**

`apps/kaipu-record/src/renderer/src/main.tsx:57`

`<RecordingShade />` no longer receives the region and phase in the URL (the old `parseShadeRect`/`parseShadeState` removal). They now arrive only as IPC state: `recording-shade-window.ts:118-126` sends once in `present`, which runs on `ready-to-show` (`181-186`). For an area take that means no pink border or REC tag for the whole take, because the recording state is not re-sent. The prewarm at app start makes this rare, but nothing handshakes it. Does the main process wait for the renderer's subscription before sending, or is the first show of a cold window exposed to this?
