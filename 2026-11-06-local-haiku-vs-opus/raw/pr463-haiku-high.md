## Findings

### 🟠🐛 **Fix · bug: Mic mute waits behind the camera reopen on the shared live-settings queue (confidence high)**

`apps/kaipu-record/src/renderer/src/features/recording/recorder-store.ts:902`

applyToggles queues the mic mute on `queue` (line 902), and so do the noise, level and volume changes. The camera reopen is queued on the same chain (lines 939-940). turnWebcamOn can hold that chain for up to WEBCAM_OPEN_TIMEOUT_MS in openWebcamWithin (recorder-engine.ts:784-787) and then for another WEBCAM_OPEN_TIMEOUT_MS in the first-frame race (recorder-engine.ts:803-808): about 6 s in the worst case. A user who turns the camera back on and then mutes the mic sees the setting flip at once (it is broadcast), but the mute is applied only after the camera settles, so the mic keeps recording in that window. Fix: keep the camera reopen on its own promise chain, so mic and audio changes never wait behind it.

### 🟠🐛 **Fix · bug: A superseded reopen closes the camera-off gap before the camera's frames are back (confidence medium)**

`apps/kaipu-record/src/renderer/src/features/recording/recorder-store.ts:943`

The 'ok' branch closes the gap whenever `webcamOn` is true when the callback runs, not when this request is still the newest. Sequence: camera on (request 1 starts opening), camera off, camera on again (request 2 queued behind it). The engine returns 'ok' for the superseded request 1 (recorder-engine.ts:810: `request !== cameraRequest` returns 'ok' while not stopped). webcamOn is now true, so `gaps.close` runs at that moment, while request 2 has not yet delivered a frame. The editor then shows the held frame as live face for the gap between the two opens. Fix: close the gap only from the request that is still current (for example, have the callback check that its request is the newest, or have the engine return a distinct result for superseded requests).

### 🟠🐛 **Fix · bug: A reopen that fails leaves the excluded bubble window on screen, while the toast says the face was recorded in the screen (confidence medium)**

`apps/kaipu-record/src/main/recording/recording-hub.ts:305`

When the camera is turned back on mid-take with the webcam file still live, the hub shows the same parked window (line 305; the replacement at line 304 is skipped because takeRecordsWebcam() is still true). That window was protected when the screen capture started, so the running capture excludes it, and camera-bubble-window.ts:262-266 keeps it as the same native window. If the reopen then fails, the recorder ends the file (recorder-engine.ts:794-799 and 814-816, then recorder-store.ts:533-537), and main only drops the protection flag (recording-hub.ts:456-460). The window is never replaced, so its face is in neither file unless the running stream honours the protection change. ADR 0032 decision 6 lists that behaviour as unverified. The post-take toast (en.json:319, 'your face was recorded in the screen instead') would then be wrong. Fix: when the webcam ends while the take's bubble is a window shown again after a park, destroy and re-show it as line 304 does, so the capture gets a new unprotected window. Add a test for this path; the hub tests cover park-then-end only, not show-then-end.

### 🟡🐛 **Consider · bug: reconcileWebcam seeds gaps without the duration that initialScene clamps them to (confidence medium)**

### 🟡📝 **Consider · docs: ADR 0032 still says hiding the bubble during a take is rejected, while decision 6 parks it (confidence high)**

`apps/documentation/src/content/docs/architecture/decisions/0032-webcam-is-its-own-track-and-the-bubble-is-excluded-from-capture.mdx:3`

The description (line 3) and the 'Alternatives rejected' entry 'Hide the bubble during the take' (line 85) say hiding the bubble during a take is rejected. Decision 6 (lines 67-81, 'hide, not destroy') parks, i.e. hides, the bubble window when the camera is turned off mid-take. The spec's decision row 3 (apps/documentation/src/content/docs/specs/2026-10-30-webcam-track-design.md:58, 'never hidden') has the same conflict with its item 7. The ADR is still Proposed, so this is not an accepted-ADR contradiction, but the front matter and the rejected-alternatives text should say the rejection covers hiding for capture exclusion, and that parking is the mid-take exception. Otherwise the next reader sees a self-contradicting record.

### 🟡📝 **Consider · docs: Spec section 3.2 still lists 'turned off' as a case where the webcam file ends (confidence high)**

`apps/documentation/src/content/docs/specs/2026-10-30-webcam-track-design.md:328`

Lines 328-329 say a take whose webcam file ended (turned off, unplugged, encoder failure) leaves the bubble in the screen capture. Under the revised item 7 (lines 86-99), turning the camera off no longer ends the file: the bubble is parked and stays protected (bubble-protection.ts:47 says the same). Only the reopen failure, unplugging and an encoder failure end the file. The parenthetical should drop 'turned off', or the section will mislead whoever reads the protection rules.

### 🟡🧪 **Consider · tests: The 'cut camera's late frame' case never reaches the relay's stale-reader branch (confidence high)**

`apps/kaipu-record/src/renderer/src/features/recording/webcam-relay.test.ts:79`

Lines 79-84 say a frame the old camera still delivers after the cut is 'dropped (and closed), not relayed'. The cut cancels the processor's readable stream, so the test's `first.push(late)` throws inside the fake's controller. The try/catch swallows the throw and the frame is never delivered to the pump. So the `current !== reader` branch in webcam-relay.ts:91-94 (which closes the frame) is not exercised, and the test never asserts that `late.close` ran. The test passes, but the comment describes behaviour it does not check. Either drive the late frame through a path that reaches the pump (for example enqueue before cut, then cut before the pump reads), or correct the comment and the test name's claim.

### 🟡❓ **Consider · question: A camera-off gap shorter than 1 s hides up to about 0.8 s of live face after the camera returns: intended? (confidence high)**

`apps/kaipu-record/src/renderer/src/features/video-editor/webcam/webcam-model.test.ts:112`

Lines 112-120 pin the stretch: a gap 3.0-3.2 s becomes a hidden segment 3.0-4.0 s, so the face stays hidden for 0.8 s after the camera is back and its frames are in the file. The stretch is the rule in webcam-model.ts:139-146, and the reason given (a segment under 1 s would not survive a reload) is in the test comment. The spec (apps/documentation/src/content/docs/specs/2026-10-30-webcam-track-design.md, section 5 and item 7) says each gap is seeded as a hidden segment, and does not mention the stretch. Is hiding live footage after a quick off/on the intended outcome, or should a short gap be dropped or stretched in the other direction? If it is intended, the spec should say so.
