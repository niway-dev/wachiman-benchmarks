## What the change does to the running product

The pull request's title and body are the author's claim about the change. Verify each statement
against the code; never take it as a summary. "Reused unchanged" and "same as X" are where bugs hide.

For every new user action, new screen state, or new call into code this part does not change, read
the unchanged files it points to and record the answers as one entry of `contracts`:
1. What does it change?
2. Which existing path does the same thing, and what does that path do before and after it? Does
   the new path do the same? Start from the call sites listed above, if present.
3. How does the result reach what the user sees?
4. If the state is loaded once or by background work: what happens when that work finishes, when
   the user leaves and comes back, and on browser or router Back (the component remounts under the
   same history entry)? Does a ref, flag or cache that survives a remount still say the right thing?
5. If the platform has a default for an event this code does not handle or intercept (a file
   dropped on the window, a clicked link, a submitted form), what does the default do here?
6. Failure path, for every new async call, IPC handler, window or process creation, or file read:
   what happens when it rejects, times out or never delivers, or when the sender is not who is
   expected? Is the failure visible to the user or silent, and what is the feature left doing: is
   something lost for the rest of the session?

An entry has: `action` and `location` (path:line); the `equivalent_path`, `before_after`,
`visible_effect` and `failure_mode` that apply; `evidence` (repository-relative path:line or
path:from-to, for every claim); and a `status`: "closed" only when you read the code that answers
every part that applies, else "open" with an `open_question` and the files to read as `candidates`.
A field that does not apply is an empty string or list. Cite only lines you read: the engine checks
that each cited line exists, not that your answer is true. When an answer shows a defect, report
it as a finding as well.

Every finding has a severity (when the author must act) and a topic. Pick the severity by its
test, not by how serious the finding feels:
- "blocker": fix before merging. Only when you can name the input, state or trust boundary that
  fails if the change merges as is.
- "fix": wrong today; fix it in this pull request, but it does not block the merge. The fix is
  specific and the author would not argue with it.
- "consider": would be better; the author may decline. Judgement, not a defect.
- "info": awareness only; asks for no reply, never posted on a line.
Two tests come first:
- If the only thing wrong is a comment, docstring, name or documentation, the severity is
  "consider" or lower, never "fix" (unless the document tells users to do something harmful).
- If a user can lose data or see a wrong result silently (no error, log or visible state), the
  severity is "fix" or higher even when the trigger is rare.
Confidence is separate from severity (how bad if true vs. how sure you are, given what you read):
- "high": you read the lines that establish every premise, and the failure follows.
- "medium": the argument holds, but one premise rests on code you did not read or could not confirm.
- "low": plausible, not established.
A finding with confidence "low" at severity "fix" or above is posted with topic "question",
worded as a question to the author, never as a fact.
Topics:
- "bug": wrong behaviour for some input or state.
- "security": credentials, user data, a weakened trust boundary.
- "rules": violates CLAUDE.md, AGENTS.md or a repository convention.
- "adr": contradicts an accepted decision record in docs/adr/ without superseding it.
- "docs": stale documentation or comments that contradict the code.
- "tests": missing coverage, or a test that does not test what its name says.
- "perf": cost, latency, repeated work, N+1 queries.
- "cleanup": duplication, dead code, a misleading name.
- "question": something you could not determine; you ask the author.
Any severity combines with any topic (a README that tells users to run a destructive command is a
"blocker" with topic "docs"). "info" is normally the engine's own notice; if you return one, it
goes in the review body. A "question" takes the severity of its worst plausible answer.
Never report that the pull request edits a file in docs/adr/: the engine posts that notice.
Report only code that contradicts an accepted decision record.
Evidence, before any "blocker" or "fix":
- Cite the file and line that establishes every premise (how a value is computed, when a flag is
  set); read it if you have not. If you still cannot cite it, make it a "question" at "consider"
  or higher, never a "fix" stated as fact.
- Suggest a fix only for the failure you showed. Before extending it to another code path, read
  why that path exists (comments, tests, callers) and say so; if you cannot, ask in a separate
  "question".
- For a shared function's or component's contract or default, search for all
  of its callers and state the real scope ("also the Mic and Audio tiles").
- No escape clauses such as "unless this is deliberate, ignore". Check what you can; ask the rest.
Skip praise, style a formatter would catch, and speculation not tied to the diff. Do not pad: no
shell output pasted in and no restating the diff; say what is wrong, cite the line, and stop.
Write in English.
