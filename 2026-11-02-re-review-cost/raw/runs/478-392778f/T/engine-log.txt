👮 **Wachiman** · 🟡🐛 **Consider · bug: Keeping `pendingInit` after an offline edit lets a later adoption silently drop that edit (confidence medium)**

An offline edit of a `pendingInit` workspace now keeps `pendingInit` and also sets `pendingIdentity` (lines 634, 638). Suppose the folder comes back holding an identity with another, unregistered id, for example one written by another Mac. `availability` then takes the adoption branch (lines 718-726): `Object.assign(entry, entryFromIdentity(...))` replaces the registry's newer name and color with the folder's values. It clears `pendingInit` but leaves `pendingIdentity` set. The next probe matches ids and "catches up" the file with values that are already the folder's (lines 670-682), so the user's rename is gone and nothing tells them.

Before this commit the edit cleared `pendingInit`, so this folder was reported as `different` and the rename was kept. The trigger is rare and needs the case you already deferred (another id in the folder). Two possible fixes: when `pendingIdentity` is set, keep the registry's name and color in the adoption branch, or refuse the adoption. Either way, also clear `pendingIdentity` there.
