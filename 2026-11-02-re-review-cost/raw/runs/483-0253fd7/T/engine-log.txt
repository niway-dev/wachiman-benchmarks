👮 **Wachiman** · 🟠🐛 **Fix · bug: Relocating the active workspace re-lists the Library before the new folder's sync provider is detected (confidence medium)**

For the active workspace, `relocateWorkspace` goes through `relocateActive` (`relocate.ts:46-48`). On commit, that calls `afterCommit` (`switch-transaction.ts:136`), which runs `host?.broadcastLibraryChanged()` (`index.ts:524-530`). So the windows re-list the Library **before** `syncStates.refresh(current)` runs here at line 755.

Until the refresh settles, `syncStates.of(active)` sees a path that differs from the cached one and falls back to `syncProviderOfPath(entry.path)` (`sync-state.ts:26-30`). That check does no `realpath` and no xattr read. A folder that only `detectSync` recognises gets `null` from it: a Drive folder reached through a symlink, or Drive mounted somewhere else and caught only by `com.google.drivefs.item-id#S` (`synced-folder.ts:80-91`). In that case `activeEvictionProbe()` returns null, and `LibraryVault` is built without a probe (`library/index.ts:72-74`). Evicted files are then listed as local and get thumbnail URLs, and the "In the cloud: download it first" state never shows.

After the refresh, this handler only calls `broadcastState()` (line 759). Nothing triggers another Library re-list, so the wrong listing stays until something else refreshes it. Nothing tells the user.

The sibling handlers detect first: `addWorkspace` refreshes at line 578 before `runSwitch` at 601, and `createWorkspace` refreshes at 630 before 635. Two possible fixes:
- Detect the provider of `chosen` before the transaction commits.
- Call `host?.broadcastLibraryChanged()` after the refresh when the relocated workspace is the active one.

I marked this medium confidence because it depends on the renderer's list request arriving before `realpath` plus the `/usr/bin/xattr` exec finish, and I did not measure that.
