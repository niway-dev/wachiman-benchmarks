👮 **Wachiman** · 🟡❓ **Consider · question: Can a probe that overlaps an edit write the old name back over the folder's identity? (confidence low)**

Nothing locks `availability` per workspace. Its new deferred-upgrade branch reads the file at line 657, checks `entry.pendingColorUpgrade` (still `true` in memory until `edit`'s `update` runs at 619-632), and then writes `{ ...identity.identity, color }` at line 684 using the snapshot it read. Here is the overlap I'm asking about. `listState` starts probe B (`index.ts:136`) just as the folder comes back, and B reads the old Default/rose file. Meanwhile an `edit` to "Studio" runs its own probe, then writes "Studio" at line 612. If B's write lands after that, the folder holds "Default workspace" and kaipu again, while the registry says "Studio" with no pending flag. The next probe finds `stale` at lines 694-699 and adopts the folder's file, so the rename is lost without any message. For this to happen, B's single write has to outlast a whole probe-write, prefs-write, read and write in `edit`, and I can't tell whether anything (for example an IPC queue) already keeps probes and edits from overlapping. Is something serializing them? If not, routing the probe's write-back branches and `edit` through one per-workspace lock would close this gap. The existing `pendingIdentity` branch at line 666 has the same read-then-write shape.
