--- apps/kaipu-record/src/main/workspaces/registry.ts:629 ---
👮 **Wachiman** · 🟠🐛 **Fix · bug: A name-only edit while the folder is away turns the deferred color upgrade into a forced write over another Mac's color (confidence medium)**

`upgradeDefaultColor` caches `color = "kaipu"` on this Mac only (line 448). Now suppose the folder is away and the user renames the workspace. `edit` keeps `color = before.color`, which is that cached `kaipu` (lines 576, 625), deletes `pendingColorUpgrade` (line 629) and sets `pendingIdentity` (line 631). When the folder comes back, the `pendingIdentity` branch writes `color: entry.color` over whatever is in the file (lines 666-671). If another Mac recoloured the Default to, say, sky in the meantime, that change is replaced with kaipu, with no message. The user never picked kaipu; only the deferred upgrade did. This breaks the promise in the docstring at line 427 ("A name or color the user already changed … on another Mac, is left as it is"), which the new yield path at line 681 exists to keep.

A possible fix: when the edit does not patch the color, keep `pendingColorUpgrade` next to `pendingIdentity`. In the `pendingIdentity` branch, write the cached color only if `isOldDefault`-style checks show the file's color is still rose; otherwise keep the file's color. The test at `registry-create-edit.test.ts:206` covers only the case where the folder did not change, so it would still pass.

👮 **Wachiman** · 🟡🐛 **Consider · bug: The deferred-upgrade write uses an identity read before an await, with no lock against a concurrent edit's folder write (confidence low)**

`availability` reads the file (line 657), checks `pendingColorUpgrade` and `isOldDefault` (line 681), then writes `{ ...identity.identity, color }` (line 684). Nothing serializes `availability` against `edit`'s `writeIdentity` (line 612): `UPDATE_LOCK` covers only the prefs write. Consider a probe that passed line 681 but whose atomic write lands after an edit's write. The probe writes back the old name, and the edit's `update` has already cleared `pendingIdentity`. The next probe then takes the folder's file as the truth (lines 693-707), and the rename is lost. The `pendingIdentity` branch at line 666 already has the same window. A per-workspace lock around the folder writes in `availability` and `edit` would close both.
